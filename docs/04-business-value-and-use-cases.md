# Why this POC matters — concrete benefits, not marketing claims

## The specific problem it solves

Cloud administrators already know how to execute Azure CLI commands. The risk with unconstrained AI automation is allowing model text to trigger privileged changes without guardrails or proof that Azure actually applied the intended configuration.

**This POC demonstrates a safer contract:** GPT translates a natural-language deployment request into a narrowly typed `deploy_storage_account` function call; local PowerShell checks the requested name, the operator confirms intent, the executor uses fixed security parameters, and Azure's live state is verified before GPT reports success.

## Demonstrated results from the CloudGenius run

| Observed | Evidence generated by running the scripts | Why it matters |
| --- | --- | --- |
| Rebuildable foundation | Foundry `cgfoundry170463`, project `cloudgenius-ai-project`, GPT deployment `cg-gpt-5-mini` | Teaches repeatable service/model setup rather than portal-only demo |
| GPT requested a tool | Console showed `GPT called: deploy_storage_account with storage_name=cgaistore610655` | Establishes function calling as a machine-readable control interface, rather than trusting free-form text |
| Human gate actually used | Console prompted for `APPROVE`; operator entered it | Prevents silent, unattended creation through this flow |
| Azure performed real deployment | Resource ID under `Microsoft.Storage/storageAccounts/cgaistore610655` and `provisioning_state: Succeeded` | Shows this was not simulated code generation |
| Policy-constrained account | HTTPS-only, TLS1_2, public network Disabled, Shared Key false, anonymous blob false | Reduces the set of accidental insecure defaults a model can select |
| Independent verification | Script queried real Azure state and returned `status: verified` | Separates cloud evidence from GPT's narrative |
| GPT wrote a report based on tool result | Successful Foundry GPT report printed after second API call | Closes the loop between intent, execution and explanation |

**Not demonstrated:** reduced costs/time measured across deployments, SOC effectiveness, successful blob connectivity over Private Link, production change audit trails, cloud-wide permissions isolation or autonomous multistep administration. Those require additional implementation and measurement.

## Five specific learning outcomes

1. **Intent is not authorization:** GPT deciding to call a tool is only a proposal.
2. **Typed interfaces reduce ambiguity:** GPT returns `storage_name` rather than unrestricted executable commands.
3. **Security policy belongs to the executor:** The script fixes `--public-network-access Disabled`, `--allow-shared-key-access false`, TLS, HTTPS and no anonymous blobs; the model cannot override these via tool arguments.
4. **Deployment != compliance:** The script separately calls `az storage account show` and verifies the expected properties before reporting success.
5. **Narration != control plane:** GPT's final report is informational; it does not finalize, lock or roll back resources.

## Expansion roadmap (future, not built)

- Move the executor into an Azure-hosted service with managed identity and **resource-group-scoped least-privilege** RBAC.
- Add formal change-ticket approval, actor identity and durable audit/event logging.
- Use IaC templates (Bicep/Terraform) with policy-as-code validation; constrain tool arguments to pre-approved changes.
- Deploy Storage private endpoint, private DNS, a VNet-connected test client and Entra Blob data-role assignment; test data plane end-to-end.
- Implement idempotent deployment, drift detection, error handling and explicit rollback/remediation plans.
- Monitor model token usage, deployments and cloud spend; establish budgets and cleanup protocols.
- Add more authorized, narrowly scoped tools (read-only inventory before any future create/update/delete).

These are proposed milestones, **not claims about the present repository**.
